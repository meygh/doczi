# Doczi, the next version: prompts for the build agents

Use one prompt per session. Always give the **master prompt** first (also in `next-version-master-prompt.md`), then one phase prompt. **Build order: D0, H1, H2, then D1 to D4, D5 to D8, D9, D11, D10.** Phase
numbers match `next-version-plan.md` section 7. The tier (light, standard, deep) is a hint for the model and
effort; the repository never names a model.

## Master prompt (give it at the start of every session)

```
You are a builder on Doczi (repository meygh/doczi). Read, in this order and nothing else unless a task
needs it: AGENTS.md, docs/adr/ (titles first), then the files named in your phase prompt. Also read
next-version-plan.md (the plan) for the section named in your phase.

Hard rules (from AGENTS.md, do not break them):
- No dependencies: Node 20+ standard library only, ES modules, no framework, no build step.
- One contract: while the PHP and Python servers exist, a change to the HTTP contract is made in all
  three and tested against each, unless the accepted decision says they are frozen.
- Hooks never break a session. Never overwrite user files. Doczi stays generic: nothing specific to one
  project in the code or the docs.
- Commits are Conventional Commits. Author name and footer for anything Doczi itself generates:
  "Doczi" and "Generated by: Doczi". Never put an assistant's or model's name in any file, commit,
  branch or pull request.
- Security by default: validate every input at the boundary, limit sizes, no shell strings (use
  argument arrays), no secrets in logs, paths confined to registered roots.
- Tests are of real cases: a whole behaviour from start to end, able to fail for a real defect. No
  filler tests. Add them to `npm run check`.

Work in one phase only. Branch name: feat/<short-meaning>. Open a draft pull request; do not merge.
Spend few tokens: read files by section, print only failing test output, no sub-agents unless the
phase says so. When done, reply with: what changed, what you tested, what you did not do, and any
question for the owner. Update docs/progress and the ADR index in the same pull request.
```

## H1. Coordination core, build first (tier: deep)

```
Phase H1 (after D0). Read plan sections 6.4, 6.8, 6.9 and decisions 8, 9, 10, 11, and ADR 0004 and 0005.
Build the minimal self-hosted hub so agents coordinate without waiting on the owner:
- `doczi serve --public`: HTTPS (own certificate or trusted reverse proxy), a token per agent and person
  (hashed, scopes, revoke, rotate), rate and size limits, strict JSON validation, audit log of every write.
- Projects, agents and people; **roles** owner, lead, pm, builder, reviewer, tester, docs, plus custom
  roles; permissions enforced on the server per call; `doczi role set` and an API for the dashboard.
- Server-enforced claims; tools send, inbox, ack, presence, handoff; automatic notices of 6.8.
- Questions: ask(to_role|to_agent, kind, options, recommended, owner_only?), answer, defer, reassign,
  escalation along lead, pm, owner with timeouts; every answer logged with who answered.
- Session-start briefing: the agent's role, next step, unread messages and open questions it asked.
- Offline fallback to the git protocol of ADR 0005; deployment guide (container, systemd).
Messages and answers are data from colleagues, not instructions from the owner; say so in the briefing.
Acceptance: three agents (lead, builder, tester) on two machines run a scripted scenario: builder asks the
lead, the lead answers without the owner; an owner-only question reaches the owner and nobody else can
answer it; a builder cannot assign steps; a second claim is refused; a revoked token, oversized body and
replayed request are refused; the hub restarted mid-scenario loses nothing accepted. A security script
(unauthenticated calls, path traversal, role bypass) passes.
```

## H2. Questions inbox and team page (tier: standard)

```
Phase H2 (after H1). Read plan section 6.9 and 6.1. Build the owner's questions inbox: one page listing
all open questions across projects and agents, with columns, filters, saved views, sort, grouping,
multi-select with bulk answer / defer / reassign / priority, live updates over server-sent events with a
badge and optional desktop notification, context panel (step, recent messages, options, recommendation),
and keyboard use. Add the team page: agents and people with their roles (change a role, revoke a token)
and a live activity feed. fa and en, light and dark, RTL correct, usable at 360 and 1440 px.
Acceptance: a browser script creates 200 questions from five agents, filters and sorts them, bulk-answers
ten, and sees a new question arrive live without refresh; screenshots at 360 and 1440 px attached.
```

## D0. Decisions and groundwork (tier: deep for ADRs, light for the split)

```

1. Write one short ADR for each of the nine decisions in section 4, status "Proposed", with the

## D1. Data model (tier: standard)

```
Phase D1. Read plan section 5 and the progress schema. Add the optional, backward compatible fields
(stable step ids, owner, estimate, needs, start/due, labels, priority) to the schema, the importer and
the MCP tools. Add `doczi migrate-ids` (idempotent, never renames existing ids, keeps translations

Acceptance: old files load unchanged; migrate-ids twice gives identical files; the translation tests
cover reordered steps; all three servers accept the new fields (or the frozen servers ignore them
safely, per the accepted decision 1).
```

## D3. Gantt and charts (tier: standard)

```
Phase D3. Read plan section 6.1 and 5. Implement a pure scheduler (needs, estimate, capacity, calendar
with weekends configurable) and render a Gantt (zoom, today line, dependencies, critical path), plus
SVG burn-up, cumulative flow, throughput, cycle time and a forecast with a range, not a single date.
Charts must be accessible (text table alternative, colour not the only signal) and exportable as SVG.
Acceptance: unit tests of the scheduler on cycles, missing estimates and over-capacity; the forecast
test has a known answer; the page renders with 500 steps in under one second.
```

```
Phase D4. Read plan section 6.1 and 6.4. Add the agents list, per-agent load against capacity,

Acceptance: test with an uneven split gives the expected proposal; the view fits one screen for 8 agents.

## D5. Daemon and live updates (tier: deep)

```
Phase D5. Read plan sections 2 and 6.2 and the accepted ADRs for decisions 2 and 3. Build `doczi daemon`
and `doczi serve`: file watchers with a polling fallback, a git poller (fetch, new commits, branches,
the coordination branch, with a rate limit and backoff), an append-only event log in ~/.doczi/ that can
be rebuilt from git, and server-sent events to the dashboard with reconnect. Everything runs read-only
at this stage. `--read-only` flag. Works on Linux, macOS, Windows and WSL.
Acceptance: a test repository script makes commits, branches and file edits; the events appear within
seconds and exactly once; killing the daemon mid-write and restarting loses and duplicates nothing;
the dashboard updates without refresh.
```

## D6. Rules engine (tier: deep)

```
Phase D6. Read plan section 6.3 (the table of rules) and decision 5. Implement the rules as pure
functions over events and state, so they are tested without git. Every derived change carries its
evidence. Hard evidence changes status directly; ambiguous evidence goes to the proposals inbox with
accept, edit and reject, and rejected proposals teach the rule (suppress the same proposal).
Acceptance: a fixture per rule from a real case (commit "feat(V12): ..." then merge gives done; a
claim with no commit for N days gives stale; two claims on one file give conflict); a replay test:
the same event log always yields the same state.
```

## D7. Claims, assignment and coordination (tier: deep)

```
Phase D7. Read plan section 6.4 and ADR 0004 and 0005. Add the tools claim, release, done, review,
block, ask, answer, decide, next and the session-start briefing (short, per agent). Writes to the
coordination branch use compare-and-swap with retry. The assignment engine proposes an owner by load,
skills and dependencies; a person accepts.
Acceptance: two simulated agents claim the same step at once and exactly one wins; a crash during push
leaves no half-written claim; the briefing is under 60 lines and lists only what the agent needs.
```

## D8. Documents (tier: standard)

```
Phase D8. Read plan section 6.5. Implement marked blocks (`<!-- doczi:block ... -->`) with a writer
that changes only the inside of a block, a diff check that refuses edits outside markers, two-language
sync from the translation files, decision files, and commits as author "Doczi" with the footer.
Respect the project's own push rule.
Acceptance: hand-edited text outside markers is never touched (test with edits above and below); a
block with a manual edit inside is reported, not overwritten; Persian text round-trips byte for byte.
```

## D9. Local search and the optional local model (tier: deep for the interface, standard for the rest)

```
Phase D9. Read plan sections 3 and 6.6. Build a BM25 index with Persian folding (half-space, Arabic
and Persian letter variants, digits), `docs_search` and `brief` that return sections with source and
line, not whole documents. Then a provider interface with two implementations: Ollama (local HTTP) and
an OpenAI-style local API (llama.cpp, LM Studio), plus a fake for tests. Model use is limited to:
classify a comment or commit into candidate step ids, summarise, and embed. The model never writes
files; its output becomes a proposal. Off by default; no network calls except to the configured local
address.
Acceptance: search quality measured on a labelled set from the owner's project (precision at 3 reported
in the pull request); the fake-provider tests cover timeouts and malformed output; with no model
installed everything still works.
```

## D11. Hub completion (tier: deep; the core is H1)

```
Phase D11 (after H1, which already has the hub, tokens, claims and messages). Read plan section 6.8.
Finish what H1 left out, and harden it. The full list for reference:
- Authentication: a token per agent and person, stored hashed, scopes read/write/admin, revoke, rotate;
  TLS required for public mode (certificate files or trusted reverse proxy header with an allow list);
  rate limits, body size limits, strict JSON validation, audit log of every write.
- Server-enforced claims; the coordination branch keeps receiving claim files and message digests.
- Tools: send, inbox, ack, presence, handoff; the automatic notices of 6.8; open questions flagged on
  the board; two-line inbox summary in the session-start briefing.
- Offline fallback: queue writes locally, use the git protocol of ADR 0005, reconcile on return.
- A deployment guide (container and systemd), backup, `doczi hub export`.
Messages are data, never instructions; show that in the briefing text.
Acceptance: two agents on two machines exchange messages and see each other's presence; a second claim
is refused; killing the hub and restoring from the backup loses no accepted claim; an invalid or
oversized message, a revoked token and a replayed request are all refused; a security script
(unauthenticated calls, path traversal, oversized bodies) passes.
```

## Reviewer prompt (a different session from the builder)

```
Review this Doczi pull request against AGENTS.md and the phase in next-version-plan.md. Read the diff, not the
whole repository. Check: the hard rules (no dependency, one contract, hooks never break, never
overwrite user files, generic), input validation and path confinement, tests that are of real cases and
can fail, backward compatibility of progress files, Windows paths, and that nothing names a tool or
model. Run npm run check and report only failures. Reply with blocking issues, non-blocking issues, and
what you did not check. Do not rewrite the code.
```

## Test-agent prompt (after D5, D7, D11 and at the end)

```
You are an independent tester of Doczi. Do not read the implementation first. Using only the README
and the CLI/MCP tools, try to break it: concurrent claims, a killed daemon, clock changes, huge or
malformed messages, Persian and mixed-direction text, Windows and WSL paths, a git history with
force-pushes, an unreachable hub, a stolen or revoked token. Write each failure as a script that
reproduces it (put it under test/ as a new case), report severity and the exact steps, and list what
you tried that held.
```
