# Plan: translate project documents in the background

Status: draft, waiting for approval · Milestone: v0.2 · Task: Translation ·
Requirements: maintainer requests of 2026-10-02 · ADR: [0002](../adr/0002-background-document-translation.md)

Replaces the "Document translation" criterion, design and steps 7–8 of
[v0.2-dashboard](v0.2-dashboard.md). Everything else in that plan stands.

## Goal

The documents a project links (requirements, plans, ADRs, README) are translated into the
project's chosen languages, on their own, in the background, into real files next to the
sources. A project served locally does this in the runtime that serves it, Node.js, PHP or
Python, on the user's machine, with a low-cost or free hosted translation service. The hosted
platform can do the same work on its server with the same formats.

## Acceptance criteria (testable)

1. **Opt-in.** Nothing is sent anywhere until the project lists languages
   (`.doczi.json` → `translate.languages`) and the user has at least one enabled provider.
   `doczi init --translate fa,de` sets the languages. Without them, init and progress changes
   queue nothing.
2. **Triggers.**
   - `doczi init` queues every linked document for every language.
   - A progress change from the CLI, MCP or any of the three servers queues one scan job.
   - The scan queues only documents whose text changed since their last translation.
   - Queueing adds under 20 ms to a progress write and never makes it fail; a hook still exits
     0 when the queue cannot be opened.
3. **Workers.**
   - With `doczi serve` running on any runtime, that server drains the queue.
   - With no server running, the Node CLI starts a detached `doczi translate --drain` that exits
     when the queue is empty.
   - Two workers never translate the same project at once (lease). A worker that died is taken
     over after 60 s.
4. **Output.**
   - `docs/i18n/<lang>/<source path>`, starting with a machine-translation notice and a
     `doczi:translated` marker (source path, source hash, language, model, date).
   - Code blocks, inline code, link targets, HTML, front matter and glossary terms come back
     byte for byte.
   - Heading anchors of the source still work in the translation, so `docs/SRS.md#m0-…` opens
     the right section of `docs/i18n/fa/docs/SRS.md`.
   - A translated file without the marker, or edited after it was written, is never overwritten.
     The job reports it as "kept".
5. **Cache and cost.**
   - A section already translated (same text, language and model) is never sent again.
   - Re-running on an unchanged project sends nothing.
   - Usage (characters sent and received, requests) is counted per provider and month.
   - A provider over its monthly budget is skipped.
6. **Limits.**
   - A 429 or 5xx response retries with backoff (honoring `Retry-After`), then moves to the next
     provider.
   - When every provider is limited, the worker pauses until the earliest reset time and says
     so in the status.
   - Every call has a 60 s timeout and a request size limit.
7. **Providers.**
   - `doczi providers list|add|test|enable|disable|remove|order`.
   - Settings live in `~/.doczi/providers.json`. A preset fills base URL and model; a custom
     base URL works too.
   - Keys come only from the environment variable the entry names. A key never appears in
     output, errors, logs, the database, the page or the project.
8. **Reader.**
   - When the dashboard language has a translation of a document, the reader shows it, with the
     notice and an "Original" switch.
   - When the translation is queued, running, outdated or failed, the reader shows the original
     with that status.
9. **Contract.**
   - `GET /api/projects/{id}/docs?path=…&lang=fa` returns the translation or the original, with
     its status.
   - `GET /api/projects/{id}/translations` returns the languages, the counts per status, a pause
     reason and the time it lifts, and per-document status.
   - Same answers from all three servers, pinned by the shared suite.
10. **Runtimes.**
    - Works with Node ≥ 22.13, PHP ≥ 8.1 with `pdo_sqlite`, and Python ≥ 3.9.
    - On Node 20 the rest of doczi works as before, and translation explains what it needs.
    - The experimental notice of `node:sqlite` never shows in the CLI, hooks or MCP output.

## Invariants touched

- **No dependencies:** SQLite and HTTPS from each runtime's own standard library only.
- **One contract, three servers:** two routes change or are added. `docs/API.md`, the contract
  suite and all three servers change in the same commit.
- **Hooks never break a session:** queueing is inside `guarded()`. It is a single insert and
  never waits for translation.
- **Never overwrite user files:** only files carrying an unchanged `doczi:translated` marker are
  rewritten.
- **Generic only:** named service presets live in one data file,
  `lib/translate/presets.json`, which goes on the project's `aiFootprint.allow` list. Rules,
  skills and agents name no service.

## Design

### Database (`~/.doczi/translate.db`, WAL)

| Table | Holds |
|---|---|
| `meta` | schema version |
| `jobs` | id, project root, kind (`scan` / `doc`), path, language, state (`queued` / `running` / `done` / `failed` / `kept`), attempts, error, not-before time, created and updated times |
| `sections` | source-section hash, language, model, translated text, created time |
| `usage` | provider id, month, requests, characters sent, characters received |
| `leases` | project root, worker id, runtime, heartbeat |
| `docs` | project root, path, language, source hash, output hash, last translated time |

- One `schema.sql` is shared by all three runtimes.
- Each runtime has a small helper (open, migrate, transaction, busy timeout of 5 s).
- Node loads `node:sqlite` lazily, only in the worker and in the queue call. Node 20 never
  touches it.

### Pipeline (per document and language)

1. Read the source and hash it. Stop if it equals `docs.source_hash` and the output is intact.
2. Split it into sections at headings. A section larger than 6,000 characters is split further
   at paragraph breaks.
3. Protect what must not change: front matter, fenced and inline code, link and image targets,
   raw HTML, URLs and glossary terms. Each becomes a numbered placeholder.
4. For each section:
   - Use the cached translation when there is one.
   - Otherwise send it with a fixed instruction: translate to the language, keep placeholders
     and Markdown structure, output only the translation.
   - Check every placeholder came back exactly once. If not, retry once, then keep the source
     text for that section and mark the job "partial".
5. Restore the placeholders. Write each source heading's id as an anchor before its translated
   heading, so source links keep working.
6. Write the file atomically, with the notice and the marker.

The glossary comes from `.doczi.json` → `translate.glossary`, plus a built-in list of common
technical terms.

### Providers

- One client for the chat-completions HTTP API.
- Presets (base URL, a default model, the usual environment variable, a terms link) live in
  `presets.json`, the only file that names services.
- The fallback chain is the order in `providers.json`. A provider is skipped while it is
  rate-limited (until the reset time) or over budget (until the next month).
- Only `https://` URLs are accepted, plus `http://` for localhost.

### Triggers and workers

| Where | Trigger | Worker |
|---|---|---|
| Node CLI / MCP / hooks | after `updateProgress` and in `init`: insert one scan job, then start `doczi translate --drain` detached when no lease is held | the detached drain process |
| Node server | after each change | in-process loop while the server runs |
| PHP server | after `changeLocked` | `php server/php/worker.php`, started next to `php -S` by the launcher; it polls every 5 s |
| Python server | after `change_locked` | a daemon thread in the server process |
| Hosted platform | its own | its own, same tables and file formats |

### Contract additions

- `GET /api/projects/{id}/docs?path=…&lang=…` returns `{ path, text, lang, translated, status,
  source }`. `status` is one of `current`, `outdated`, `queued`, `running`, `failed`, `kept`,
  `none`. Without `lang` the route answers as today.
- `GET /api/projects/{id}/translations` returns `{ languages, counts, paused, resumesAt, docs:
  [{ path, lang, status, error? }] }`. Error texts never contain keys or document text.
- MCP: `translate_status` and `translate_queue`.

### Dashboard

- The reader picks the translation that matches the interface language. It shows the notice,
  an "Original" switch and a status line ("Translating…", "Out of date, update queued",
  "Failed: …").
- A small "Translations" line in the overview shows the counts and the pause reason.

## Test plan

- **Shared fixtures** (`test/fixtures/translate/`): sources with code, links, HTML, front matter
  and glossary terms, and the expected sections and placeholders. One suite runs them against
  Node, PHP and Python, the same way the contract suite does.
- **Fake provider:** a local HTTP server that "translates" by wrapping text. Scripts make it
  answer 429 with `Retry-After`, 500, a timeout, a dropped placeholder, or a huge reply.
- **Queue:**
  - concurrent workers from two runtimes never hold one project at once;
  - a stale lease is taken over;
  - a crashed `running` job returns to `queued`.
- **Triggers:**
  - progress writes from the CLI, MCP and each server queue exactly one scan;
  - the queue failing never fails the write;
  - a hook with an unwritable home still exits 0.
- **Output:**
  - anchors resolve;
  - an edited translation is kept;
  - a second run on an unchanged project sends zero requests;
  - writes are atomic.
- **Security:**
  - keys never appear in stdout, stderr, the database, errors or HTTP answers;
  - provider URLs are validated;
  - paths outside the project are refused;
  - the translated-document route reads only `docs/i18n/<lang>/` paths of linked documents.
- **Runtimes:** Node 20 skips translation with its notice; CI runs Node 20, 22 and 24.
- **By hand:** translate this repository's README and API docs into Persian with a free hosted
  model on each runtime, and read them in the dashboard.

## Risks

- **Free tiers are small and change often.** 50 requests a day fill on the first run of a
  large document. The cache and the pause-until-reset keep later days small. Presets are data,
  so they can change without code.
- **Free tiers may keep or train on the text.** Opt-in per project, and terms links in
  `doczi providers list`. The README recommends a paid low-cost provider for private documents.
- **Three copies of the pipeline drift.** The shared fixtures and the fake provider run against
  every runtime in CI.
- **`node:sqlite` is experimental before Node 25.7.** Keep it behind one helper; pin its
  behavior in tests.
- **SQLite on network drives.** WAL needs a local disk. `~/.doczi` is local by default;
  document it.
- **Machine translation can be wrong.** The notice on every file, the "Original" switch, and
  hand edits are kept.
- **The installed hook from the old plugin name** does not read `.doczi.json` and blocks service
  names everywhere. Reinstall the plugin as doczi before step 4, or `presets.json` cannot be
  written.

## Open questions

1. Which documents: only those the progress file links (recommended, small and deliberate), or
   every Markdown file under `docs/`?
2. Should `doczi init` ask for languages and offer to add a provider, or only take
   `--translate`?
3. Default monthly budget per provider. 2 million characters is my suggestion: about 30 large
   documents, and a few cents on a low-cost paid service.
