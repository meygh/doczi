# Plan: v0.2 dashboard, task types, import/export, languages and translation

Status: approved, in progress · Milestone: v0.2 · Requirements: maintainer requests of 2026-10-01

Shared storage for several people (a database) is not in this plan. It depends on the hosted
platform decision; see "Out of scope" at the end.

## Goal

Make the tracker easier to read and to fill, in more languages:

- clearer task bars;
- a "Needs you" panel that can be hidden and collapsed;
- types and tags on tasks;
- import of tasks from requirement documents, and export of the tracker;
- the dashboard in six languages;
- optional translation of project documents through providers the user manages.

## Acceptance criteria (testable)

1. **Task bars.** Every task row shows a bar at least 8 px high, its percentage, and a legend
   of the done, waiting and in-progress colors, readable when the task is collapsed. Contrast
   meets WCAG 2.2 AA in the light and dark themes.
2. **Needs you panel.**
   - The panel can be shown or hidden. Its three groups (Blocked, Waiting for your check,
     Questions) collapse one by one.
   - The choices are remembered per browser and per project.
   - When the panel is hidden but has items, the header shows a count badge.
3. **Types and tags.**
   - A task may have a `type`: `feature`, `bug`, `issue`, `refinement`, `redesign`, `chore`,
     `docs`, `research` or `security`.
   - A task may have up to 10 `tags`, each a short lowercase text.
   - The validator, the schema and all three servers accept both fields.
   - The dashboard filters by type and by tag. The CLI and MCP can set both.
4. **Import.**
   - `/doczi:import-tasks <doc>` reads a requirements or plan document and proposes milestones,
     tasks and steps, each linked to its section (`docs/SRS.md#fr-12`).
   - Nothing is written until the user approves.
   - `doczi import <file.md>` does the same without an agent, for Markdown checklists and
     headings.
   - Running the import again adds only new items; nothing is duplicated.
5. **Export.**
   - `doczi export --format md|csv|json` writes the tracker to a file, never over an existing
     one.
   - The dashboard has a "Download as Markdown" and a "Download as CSV" button.
6. **Interface languages.**
   - The dashboard is available in English, Persian, German, Arabic, Turkish and Spanish.
   - It follows the browser language, with a menu to override it.
   - Persian and Arabic switch the page to right-to-left.
   - Untranslated strings fall back to English.
   - A test fails when a translation file is missing a key or has an extra one.
7. **Document translation.** Superseded by [v0.2-translation](v0.2-translation.md) (background
   queue in every runtime, ADR 0002); kept here for the record.
   - `doczi translate <doc> --to fa` writes `docs/i18n/fa/<doc>`.
   - Code blocks, inline code, links, front matter and glossary terms stay in English.
   - It refuses to overwrite a file the user edited by hand.
   - Providers, models and keys are managed in the user's own settings, never in the project
     repository.
   - The dashboard reader offers the translated version when one exists.

## Invariants touched

- **One contract, three servers.**
  - The type and tag fields go into `docs/API.md`, the schema, the contract tests and every
    server.
  - Translation and import run only in the Node CLI and MCP server. The HTTP servers only
    serve translated files.
- **No dependencies.**
  - Providers are called with the built-in `fetch`, with a timeout and a size limit.
  - Markdown handling reuses the existing safe subset.
- **Never overwrite user files.** Import, export and translate write new files, or change the
  progress file only under the lock.
- **Security.**
  - API keys are kept outside the project and are never logged or sent to the page.
  - Document text is sent only to the provider the user configured.

## Design

- **Types and tags** are optional task fields. `summarize` adds per-type counts. The filter
  bar gets a type menu and tag chips. The step line format does not change.
- **Needs you panel:**
  - a header toggle (`aria-expanded`) and one `<details>` element per group;
  - state kept in `localStorage` under `doczi.attention.<project>`, read and written inside
    try/catch.
- **Interface languages:**
  - one file per language, `web/i18n/<lang>.json`, holding flat keys and `{name}`
    placeholders;
  - every visible string in `app.js` and `index.html` goes through `t(key, values)`;
  - `dir="rtl"` on `<html>` for Persian and Arabic, with CSS logical properties
    (`margin-inline-start` and similar) instead of left and right;
  - the selected language is remembered per browser.
- **Translation providers.** Settings live in `~/.doczi/providers.json`, outside every project
  repository.
  - A provider entry holds an id, a kind, a base URL, a model, the name of an environment
    variable that holds its key, a monthly character budget and an `enabled` flag.
  - There are three kinds:
    1. `chat-completions`: the common chat-completions HTTP shape that most hosted free tiers
       and local model runtimes accept;
    2. `deepl`;
    3. `ollama`: local, no key.
  - `doczi providers list|add|test|enable|disable|remove` manages them. The order of the list is
    the fallback order.
  - Usage is counted per month in `~/.doczi/usage.json`.
  - There is no key entry in the dashboard in this version.
- **Translation pipeline:**
  1. Split the document by heading.
  2. Replace code, links, front matter and glossary terms with placeholders.
  3. Translate each chunk, with an instruction to keep the placeholders and technical terms.
  4. Check that every placeholder came back.
  5. Restore the placeholders.
  6. Write the output with a header recording the source file's hash.

  The glossary comes from `.doczi.json` → `translate.glossary`, plus a built-in list of common
  technical terms. Unchanged sections are not sent again (cache by section hash).
- **Import:**
  - The skill does the understanding: it maps requirement IDs to tasks and proposes a diff.
  - The CLI importer is deterministic: `## heading` becomes a task, `- [ ]` and `- [x]` become
    steps, and IDs like `FR-12` become document anchors.
  - Both write through `updateProgress` under the lock.

## Test plan

- **Unit:**
  - validator and schema with types and tags (valid, unknown type, too many tags);
  - summarize counts per type;
  - CSV and Markdown export;
  - the importer on fixture SRS files, including idempotence;
  - placeholder protection: a code block, a link and a glossary term survive a fake provider
    that rewrites everything else;
  - a provider timeout, a 429 response and a missing key each give a clear error;
  - the budget stops a run.
- **Contract:** types and tags round-trip on Node, PHP and Python.
- **Dashboard:**
  - i18n key parity across all six files;
  - the RTL layout at phone width;
  - Needs you hide and collapse state survives a reload;
  - the type and tag filters.
- **Security:**
  - keys never appear in output, errors or the progress file;
  - translate refuses paths outside the project;
  - provider URLs must be http(s), and plain http is allowed only for localhost.

## Risks

- **Free tiers change often, and some free tiers may use the submitted text for training.**
  The provider list shows each provider's terms link. A local model is the private option.
- **Machine translation of technical documents can be wrong.** Each output carries a "machine
  translated" banner, and the source stays the reference.
- **Wording in RTL languages.** A native speaker should review the Persian and Arabic.
- **Size.** About 300 strings × 6 languages adds maybe 60 KB to the page, which is fine without
  a build step.

## Out of scope: shared storage and the hosted platform

Sharing one project between several people on different machines needs:

- a server that everyone can reach;
- accounts and permissions;
- a database.

That conflicts with two current rules: the server runs on localhost only, and there are no
dependencies. It belongs in a separate hosted service. The local plugin syncs to it, and the
file in git stays the source of truth for the agents. Decide it together with the company
platform's stack.
